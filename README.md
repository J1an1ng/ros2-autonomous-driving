# Team 20 Autonomous Driving — ROS 2 Jazzy

This repository contains Team 20's autonomous-driving project for the Introduction to
ROS course. The ROS 2 workspace is in [`project/`](project/). It uses the supplied Unity
simulator and drives a predefined route with regular RGB-D perception, route and
trajectory planning, decision making, and closed-loop vehicle control.

The complete production system is started by one launch file. No production node needs
to be started manually in a separate terminal.

## 2. Capabilities and architecture

The production system can:

- start the supplied Unity simulator and all production ROS nodes from one launch file;
- receive vehicle pose/velocity, normal RGB images, metric depth, camera calibration,
  IMU data, and TF;
- detect vehicles and traffic lights with YOLOv8n ONNX on the normal RGB camera and
  estimate vehicle range using depth reprojection;
- publish filtered point clouds, a projected occupancy map, and a 3-D OctoMap;
- follow a validated 64-waypoint route and publish local route context and speed limits;
- generate a smoothed, curvature-checked trajectory with per-point target speed and time;
- stop/release at the four controlled traffic-light areas, follow a slower vehicle, and
  handle merging or emergency obstacle risk according to an explicit safety priority;
- track the timed trajectory with Pure Pursuit steering and PID speed control; and
- fail safe when required sensor, TF, planning, or decision input is missing or stale.

Production perception uses regular RGB, depth, calibration, and TF. The Unity semantic
camera is disabled and is not used by the autonomy stack.

```text
Unity sensors ──> perception ──> vehicle/light observations ───────┐
Unity pose ──> route_manager ──> trajectory_generator ──┐          │
                                                       ├─> decision_making
                                   planning trajectory ┘          │
                                                                  │
Unity velocity/TF ──> controller <── trajectory + final speed/stop┘
                           │
                      /car_command ──> Unity
```

The principal safety boundary is that `decision_making` owns the final permitted speed
and stop intent, while only `controller_node` converts that intent into `/car_command`.
The complete node/topic graph and ownership labels are available in
[`project/docs/ros_graph.svg`](project/docs/ros_graph.svg).

## 3. Supported environment

Use the assessed environment:

- Ubuntu 24.04 with a graphical Linux session and working OpenGL;
- ROS 2 Jazzy Jalisco Desktop;
- Git and Git LFS;
- `rosdep`, `colcon`, and the standard ROS build tools.

Ubuntu 22.04, WSL, containers, and remote displays are not the assessed platform. The
bundled simulator is a Linux executable.

Install the basic tools if needed:

```bash
sudo apt update
sudo apt install git git-lfs python3-colcon-common-extensions python3-rosdep
git lfs install
```

Install ROS 2 Jazzy Desktop using the official
[ROS 2 Jazzy installation instructions](https://docs.ros.org/en/jazzy/Installation.html).
Confirm that `/opt/ros/jazzy/setup.bash` exists, then initialize `rosdep` once on a new
machine:

```bash
sudo rosdep init
rosdep update
```

If `rosdep init` reports that its sources already exist, run only `rosdep update`.

## 5. Install dependencies and prepare Unity

From the repository root:

```bash
cd project
source /opt/ros/jazzy/setup.bash
rosdep update
rosdep install --from-paths src --ignore-src -r -y
bash src/setup_script.sh
```

The setup script marks the supplied Unity executable and helper scripts as executable.
The production YOLOv8n ONNX model and ONNX Runtime are included in the perception
package. Ultralytics Python is required only for optional model training/export, not for
normal operation.

## 6. Build and test

Stay in `project/` and run:

```bash
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install
source install/setup.bash
colcon test
colcon test-result --verbose
```

The final command must report zero failures and zero errors. In every new terminal,
source ROS and the built workspace again:

```bash
source /opt/ros/jazzy/setup.bash
source <repository-path>/project/install/setup.bash
```

Replace `<repository-path>` with the absolute path to this clone.

## 7. Launch the complete system

### Safe readiness check

The following single command starts Unity, the ROS bridge, sensor TF, perception,
mapping, route management, trajectory generation, decision making, the production
controller, and visualization. Motion remains disabled:

```bash
cd project
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 launch system_bringup full_system.launch.py \
  route_initial_waypoint_index:=0 \
  enable_motion:=false \
  enable_visualization:=true
```

Wait until Unity is connected, 64 waypoints are loaded, the YOLO model is loaded, RGB
and depth data arrive, and TF `world -> OurCar/INS` is available. Startup warnings about
missing input are expected until the first simulator messages arrive; the controller
brakes while required inputs are missing or stale.

Stop the readiness launch with `Ctrl+C` before starting a moving run.

### Normal moving launch

After the readiness check, the same launch file can authorize motion:

```bash
ros2 launch system_bringup full_system.launch.py \
  route_initial_waypoint_index:=0 \
  enable_motion:=true \
  enable_visualization:=true
```

This is the required one-launch-file entry point. Never start the supplied
`dummy_controller` at the same time: the production `controller_node` must be the only
publisher of `/car_command`.

### Recorded and audited full mission

For a waypoint 0–63 validation run with rosbag recording, logs, figures, and automatic
auditing, use the wrapper around the same production launch:

```bash
python3 tools/run_full_mission.py --visualization
```

Omit `--visualization` to reduce RViz load. A successful run prints `Route completed at
waypoint 63`, checks the recorded route and trajectory, and regenerates `mission_results/`
(repository path `project/mission_results/`). An interrupted or failed run preserves the
previous valid result.

## 8. Verify a live run

In a second sourced terminal:

```bash
ros2 node list
ros2 topic hz /OurCar/INS/twist
ros2 topic hz /planning/path
ros2 topic hz /planning/trajectory
ros2 topic echo /route/current_waypoint_id
ros2 topic echo /decision/state
ros2 topic echo /perception/traffic_light_state
ros2 topic info /car_command
```

Expected results include continuous sensor/planning updates, finite trajectory points
with increasing `time_from_start`, appropriate following and traffic-light states, and
exactly one `/car_command` publisher named `controller_node`.

## 9. Important launch arguments

| Argument | Default | Purpose |
| --- | --- | --- |
| `start_unity` | `true` | Start the bundled Unity simulator. |
| `sensor_bind_host` | `127.0.0.1` | Bind address of the TCP sensor receiver. |
| `enable_motion` | `false` | Permit the production controller to move the vehicle. |
| `enable_visualization` | `true` | Start live visualization and the two RViz views. |
| `route_initial_waypoint_index` | `0` | Start index; use `0` for the assessed complete route. |
| `enable_perception` | `true` | Start YOLO RGB-D perception and mapping. |
| `enable_octomap` | `true` | Start OctoMap. |
| `enable_route` | `true` | Start route management. |
| `enable_trajectory` | `true` | Start trajectory generation. |
| `enable_decision` | `true` | Start obstacle monitoring and decision making. |
| `enable_controller` | `true` | Start Team 20's production controller. |
| `simulation_config` | installed default | Absolute path to a compatible Unity `simulation_config.json`. |
| `yolo_model` | installed `yolov8n.onnx` | Absolute path to a compatible ONNX perception model. |
| `route_file` | installed `route_map.yaml` | Absolute path to a compatible route YAML file. |
| `wheelbase` | `2.63` | Shared planner/controller bicycle-model wheelbase in metres. |
| `maximum_steering_angle` | `0.52` | Shared planner/controller steering limit in radians. |

Default file arguments resolve to matching files installed from this revision. Planner
and controller receive the same vehicle-model arguments; the controller independently
rejects trajectories outside its curvature boundary.

## 11. Safety boundaries and known limitations

This project is designed and validated only for the supplied simulator. Do not deploy
the controller on a physical vehicle without a separate hazard analysis, hardware safety
layer, vehicle-interface validation, and closed-course testing.

- `enable_motion` defaults to `false`; explicitly enable it only after Unity, sensors,
  TF, perception, planning, and decision making are ready.
- `/car_command` must have exactly one publisher. Never run `dummy_controller`, manual
  commands, or another controller together with the production controller.
- Missing or stale required inputs, infeasible trajectory geometry, and stop requests
  produce braking rather than continued motion on old data.
- The global route is fixed and does not replan when the map or mission changes.
- Traffic-light selection uses route gates and calibrated image regions; camera, map, or
  route changes require recalibration and a new complete-route validation.
- The distributed model is a COCO-pretrained YOLOv8n baseline rather than a Team 20 model
  fine-tuned on Unity data.
- Trajectory generation constrains curvature and acceleration but does not model jerk,
  tyre-force coupling, steering rate, drivetrain dynamics, or free-space obstacle path
  replanning. Obstacle risk is handled through longitudinal decisions and safe stopping.

## 12. Troubleshooting

If Unity or the YOLO model is missing, retrieve the LFS assets and prepare Unity again:

```bash
git lfs pull
cd project
bash src/setup_script.sh
```

If ROS cannot find packages or launch files, rebuild and source the workspace:

```bash
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install
source install/setup.bash
```

If the vehicle does not move, confirm `enable_motion:=true`, the Unity connection, TF,
vehicle velocity, a fresh trajectory, and fresh decision messages. A missing or stale
required input deliberately produces a safe brake command.

If commands conflict, run `ros2 topic info /car_command` and stop the
`dummy_controller`, teleoperation, or any manual command publisher.
